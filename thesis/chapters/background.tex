\subsection{Sparse Matrix Storage Formats}
The four formats considered in this work represent the standard vocabulary of sparse
matrix storage. Compressed Sparse Row (CSR), see Figure~\ref{fig:csr}, stores non-zeros row by row, with a row
pointer array enabling efficient traversal of row entries.
Compressed Sparse Column (CSC), see Figure~\ref{fig:csc}, is the column-major analog to CSR; columns are stored
contiguously, making it efficient for column-wise access patterns. Coordinate format
(COO), see Figure~\ref{fig:coo}, stores each non-zero as an explicit $(\text{row}, \text{col}, \text{value})$
triple, meaning more memory per entry and
imposing a scan cost proportional to the total non-zero count during either row-wise or column-wise access.
Dense format stores all elements explicitly in a flat row-major array, eliminating
indexing overhead entirely and making any access pattern possible, making it optimal
when most entries are non-zero, unsurprisingly. Each format encodes the same matrix
but makes different trade-offs between storage overhead and the best access pattern.
A standard reference for these formats in the context of sparse linear algebra
compilers is TACO \cite{taco_formats}, who provide a unified description of
format capabilities in terms of per-dimension storage modes.

\subsection{SpGEMM}
SpGEMM computes $C = A \times B$ where $A$ and $B$ are sparse matrices. Unlike sparse
matrix-vector multiplication (SpMV), SpGEMM involves two sparse operands whose
non-zero structure interacts during multiplication: the output sparsity pattern is not
known in advance and meaning many implementations compute the output symbolically before any actual numeric accumulation can
begin. The operation appears as a core subroutine in algebraic multigrid solvers,
triangle counting, multi-source breadth-first search, and high-dimensional similarity
search, among many other applications~\cite{spgemm_survey}.
Buluç and Gilbert~\cite{buluc_gilbert}
provide foundational parallel algorithms for SpGEMM.
The most performance-relevant observation for this work is that SpGEMM is overwhelmingly
memory-bound on current hardware. The irregular, format-dependent access patterns of
sparse operands generate large numbers of short, hard to predict memory requests, keeping
arithmetic units underutilized.

\subsection{SpGEMM Dataflows}
In SpGEMM, only products in which both
$a_{ik}$ and $b_{kj}$ are non-zero contribute, I will call this quantity \emph{matches}, since only values which 'match up' in both matrices will
contribute non-zero output values. The three indexing variables $i$, $j$, $k$ naturally give a triple loop nest, and
which loop is innermost determines the \emph{dataflow}, that is, the order in which
non-zeros of the inputs are read and results are computed.
Because a compressed matrix can be traversed efficiently only along its
storage order, the choice of dataflow and the choice of formats are very tightly
coupled. Table~\ref{tab:dataflows} summarizes the dataflows of interest to this thesis.

\paragraph{Inner product ($i,j,k$).}
Each output element is computed as the dot product of a row of $A$ and a column
of $B$, which is most conducive when one operand is stored row-major and the other
column-major (best represented as CSR$\times$CSC). The two index lists must be \emph{intersected},
and depending on density and structure, often most comparisons find no match, so non-zeros are unfortunately fetched and discarded.
Each $c_{ij}$ is finished in one pass, which gives good output reuse, but input reuse
is poor and every possible output position must be examined even though the
result is often sparse \cite{srivastava2020matraptor,zhang2020sparch}.

\paragraph{Outer product ($k,i,j$).}
This dataflow is expressed as a sum of partial matrix products, $C = \sum_k A_{:,k}B_{k,:}$,
pairing a column of $A$ with the matching row of $B$ (best represented as CSC$\times$CSR). No index
matching is required and every non-zero of $A$ and $B$ is read exactly once,
however each term yields a partial result matrix, and all of them must at some point be
reduced, giving poor output locality and intermediate storage that grows with the
number of matches \cite{pal2018outerspace,zhang2020sparch,bulucgilbert2008hypersparse,bulucgilbert2010highly}.

\paragraph{Row-wise product / Gustavson ($i,k,j$).}
For each row of $A$, every non-zero $a_{ik}$ selects row $k$ of $B$, which is
scaled and accumulated into a row buffer holding row $i$ of $C$ (best represented as CSR$\times$CSR,
the column-wise analog as CSC$\times$CSC) \cite{gustavson1978}. It avoids index matching because the row pointer array
gives direct access to row $k$ of $B$, and it keeps the output row in the
accumulator, and each element of $A$ is touched only once, but reuse of rows of $B$ across rows of $A$ is irregular
\cite{zhang2021gamma}.

\paragraph{Accumulating partial products.}
Row-wise and outer-product algorithms must combine any partial products that
land on the same output position. Common accumulators include the dense
\emph{sparse accumulator} (SPA) \cite{gilbert1992matlab}; hash tables; and heaps or sorted
merges. Of course, their costs and trade-offs differ \cite{nagasaka2018highperformance}.
Implementations also differ in whether the
output structure is computed in a separate symbolic phase or
allocated from an upper bound, which trades extra computation against extra memory
\cite{nagasaka2018highperformance}. TACO defaults to a symbolic phase and many format combinations require specific
scheduling commands to utilize any output accumulators. For the most part, this thesis ignores output accumulation.
Most analysis later in the thesis will assume that accumulation can be done separately as a post processing step.

\paragraph{Relevance to format selection.}
Format pairs therefore largely determine the dataflow a compiler can reasonably generate,
so the comparison of format combinations in Chapter~\ref{ch:pact} and Chapter~\ref{ch:kron_taco} are, in part,
comparisons of dataflows.

\subsection{BLIS}
The BLAS-like Library Instantiation Software (BLIS) framework~\cite{blis} provides a
portable infrastructure for implementing dense level-3 BLAS operations. Its key insight
is that virtually all computation in dense matrix multiplication can be expressed in
terms of a small, hardware-specific micro-kernel operating on dense register-sized
panels, surrounded by a fixed five-loop blocking structure parameterized by cache-level
constants $m_c$, $n_c$, $k_c$ and micro-kernel block sizes $m_r$ and $n_r$. This
separation allows the bulk of the framework to be written once in portable C while
performance-critical sections are tuned per architecture. This thesis includes a chapter on an
implementation which preserves this five-loop structure and blocking hierarchy, replacing only the innermost
micro-kernel with a dispatch over heterogeneous sparse formats.

\subsection{Roofline Model}
The roofline model~\cite{roofline} provides an upper bound on achievable kernel
performance as a function of arithmetic intensity (FLOPs per byte of memory traffic).
For a given kernel and machine, the model draws a ``roofline'' as the minimum of the
peak compute throughput and the product of memory bandwidth and arithmetic intensity. A
kernel is compute-bound if its arithmetic intensity exceeds the machine's
compute-to-bandwidth ratio, and memory-bound otherwise. SpGEMM kernels consistently
fall in the memory-bound regime due to low data reuse and irregular access patterns, see Chapter~\ref{ch:pact}.

\subsection{TACO}
The Tensor Algebra Compiler (TACO)~\cite{taco} automatically generates
kernels for compound tensor algebra expressions over mixed dense and sparse tensors,
including most format combinations relevant to this thesis. TACO provides a formalization of how
iteration spaces and index expressions vary across storage formats,
and its generated kernels served as the main reference for Chaper~\ref{ch:kron_taco}, as well as the starting
point and correctness reference for Chapter~\ref{ch:pact}'s
hand-instrumented implementations.

\subsection{Kronecker Graphs}
Kronecker graphs~\cite{kronecker} are a family of self-similar synthetic networks
generated by repeated Kronecker product of a small initiator matrix with itself. They
were introduced as a model for real-world networks because their recursive structure
naturally produces the heavy-tailed degree distributions and small diameters observed
in real-world internet topology graphs and social networks. The datasets described in Chapter~\ref{ch:kron_taco}
are standard benchmark graphs which can represented as Kronecker graph instances, and which form the main datasets used for the experiments of this thesis.
These were all generated using mfit \cite{moez}
